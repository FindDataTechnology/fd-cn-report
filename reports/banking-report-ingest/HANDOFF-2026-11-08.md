## 7. 仓库与并发（这条差点让我把别人的修复推回去）

`fd-cn-report`、`fd-industry-data` 都是**双远端**：gitee 主开发，GitHub 跑 Actions 并自动回写
`reports/**`，并发的另一个会话也在推。非快进是常态。

**不要 `git pull` 硬拉**——工作树里有并发会话未提交的改动，一拉就搅在一起。
做法是临时克隆：

```bash
git clone -q <repo> /tmp/sync && cd /tmp/sync
git remote add gh git@github.com:FindDataTechnology/<repo>.git
git fetch gh main && git rebase gh/main && git push gh HEAD:main
```

### 7.1 三条硬规矩

1. **判一致要比文件内容，不要用 `merge-base --is-ancestor`**：rebase 后哈希全变，
   它会告诉你「不一致」，而内容其实一模一样。
2. **rebase 冲突不要整体取一边**。一次只有 1 个文件报冲突，但 `git diff --stat gh/main..HEAD`
   会露出**另外几处**「你没改、却与远端不同」的文件——那是 rebase 把你的旧版重放上去了。
   2026-11-08 实测：`cncotton/manifest.yaml`（GitHub 已 `parked: true`，我这边是旧 `schedule`
   ⇒ 推上去就恢复每月假红）、`restaurant-alerts/state/last-fired.json`（GitHub 是 08:33:59
   工作流产出的 4 条，我这边是 08:32 的手工清空 ⇒ 推上去等于用过期状态覆盖）。
   正确做法：**逐文件看哪侧更新**再取，别整体 `--ours` / `--theirs`。
3. **推之前确认净改动只有你自己的东西**：
   `git diff --stat gh/main..HEAD` 应当只列你改的文件。多出来的就是被重放的旧版，
   必须逐个处理掉再推。那次的终态是「34 行新增、零删除」。

### 7.2 判断「哪侧更新」不能看 diff 方向（我在同一个文件上错了两次）

`git diff gh/main..HEAD -- <file>` 里的 `+parked / -schedule` **只表示从远端到本地的变化**，
它既可能是「远端缺这个修复」，也可能是「我要把它回退掉」——两种情况长得一模一样。

2026-11-08 在 `spiders/cncotton/manifest.yaml` 上连续错两次：
第一次以为本地旧，强取 GitHub ⇒ 把已修好的 `parked: true` 覆盖回 `schedule`；
第二次方向改了，但又差点整体取一侧。

**正确做法是丢掉 diff 直觉，直接看每一侧的实际内容**：

```bash
grep -E "^parked:|^schedule:" <file>                      # 本地
git show gh/main:<file> | grep -E "^parked:|^schedule:"   # 远端
```

判定依据是**语义**（`parked: true` 是新版、`schedule:` 是会让停更源每月假红的旧版），
不是 `+`/`-` 的朝向。

### 7.3 别拿「自己改坏的版本」当基准（自证陷阱）

第一次误覆盖后我核对「五个文件两端一致」→ 全部 ✓。但那个 ✓ 是假的：
我比的是**被我改坏的本地** 与 **被我推上去的 GitHub**，两边当然一样——
**自证**，不检验任何东西。

核对一致性之前，先确认基准本身是对的：拿**已知正确的期望内容**（这里就是
`parked: true`）去比两侧，而不是让两侧互相比。

### 7.4 收尾动作

推完把同一份文件同步回本地（`git checkout <临时分支> -- <路径>`），否则本地会越拖越偏；
临时目录用完即删。
